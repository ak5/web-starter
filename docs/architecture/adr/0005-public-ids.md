# ADR 0005 — Prefixed public IDs everywhere

**Status:** Accepted

## Context

Every row has an internal primary key for joins. The naive choice is to expose
that PK in API responses, URLs, and JWTs. Sequential or guessable internal keys
leak two things: **scale** (a competitor can read `id=5012` and learn how many
users exist) and **structure** (the same identifier used internally for joins is
now pasted across logs, client code, and shareable links, coupling the wire
format to the storage layer). We want external identifiers that reveal neither.

## Decision

Give every externally-visible entity a **prefixed public ID** generated by
`customAlphabet('0123456789abcdefghijklmnopqrstuvwxyz', 10)`, with a short
type prefix: `u-` (user), `a-` (admin), `t-` (token), and so on. The internal
sequential / nanoid PK **never leaves the database** — it appears only in joins.
All API responses, URLs, JWT `sub` claims, cookies, and client-side code use the
public ID exclusively. The generator lives in `packages/shared/src/public-id.ts`.

> **Rule: never expose internal IDs.** All API responses, URLs, JWTs, and
> frontend code use `publicId` (prefixed). Internal PKs exist only for joins —
> they never appear in JSON responses, URL params, cookies, or client-side code.

## Consequences

- **No enumeration:** a 10-character base-36 random ID is not guessable or
  walkable, so endpoints do not leak counts or let an attacker iterate entities.
- **No PK leakage:** the storage key stays internal, so the wire format is
  decoupled from the table's primary key — we can change the internal key strategy
  without breaking any external reference.
- **Self-describing references:** the prefix makes IDs legible in logs and bug
  reports (`u-…` is obviously a user), and lets validation reject a token ID where
  a user ID is expected.
- Cost: a second identifier per row and an index on `public_id`; every boundary
  must translate PK ↔ public ID. This is mechanical and centralized in the data
  layer.

## Alternatives considered

- **Expose the sequential PK:** simplest, but leaks counts and couples wire to
  storage — the exact problems this ADR exists to prevent.
- **Random UUIDs as the PK:** removes enumeration but makes every internal join key
  a bulky random value and still couples external refs to the storage key. The
  split (small internal PK + separate public ID) keeps joins cheap and the
  external surface clean.
